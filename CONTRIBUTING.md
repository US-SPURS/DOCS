# Contributing to US-SPURS Documentation

Thank you for contributing to the United States Department of Special Projects and Unified Response Services documentation ecosystem.

## Contribution Standard

All contributions should be clear, reviewable, secure, and tied to a real organizational, technical, or operational need.

## Before You Start

1. Review the repository README and the `spurs/` documentation set.
2. Search existing issues and pull requests.
3. Create or reference an issue for substantial work.
4. Confirm that sensitive or restricted information is not being introduced into a public repository.

## Acceptable Contributions

- documentation corrections and expansion
- architecture and integration guidance
- operational doctrine and playbooks
- developer onboarding improvements
- repository automation and quality controls
- accessibility and usability improvements

## Branches

Use a focused branch name such as:

- `feature/short-description`
- `fix/short-description`
- `docs/short-description`
- `security/short-description`
- `chore/short-description`

## Pull Requests

Every pull request should explain:

- the problem being addressed
- what changed
- why the approach was selected
- how the change was validated
- any security, operational, or compatibility impact

Keep pull requests focused. Unrelated changes should be separated.

## Documentation Quality

Documentation should:

- use precise language
- avoid unsupported claims
- distinguish current capability from future intent
- define acronyms and specialized terms
- use consistent US-SPURS naming
- remain readable to both technical and nontechnical audiences

## Technical Quality

Where code or configuration is involved:

- run tests and validation
- avoid hard-coded secrets
- document new dependencies
- preserve backward compatibility when practical
- include failure handling and observability
- update related documentation

## Security

Do not open a public issue containing credentials, private keys, protected personal data, vulnerabilities that create immediate exposure, or sensitive operational information. Follow `SECURITY.md` instead.

## Review

Changes may require documentation, technical, security, operational, or leadership review depending on impact.

## Definition of Done

A contribution is complete when the change is correct, validated, documented, reviewable, and aligned with the repository's mission and standards.
