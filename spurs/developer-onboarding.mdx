# Developer Onboarding

This page provides the baseline onboarding path for engineers, technical writers, systems architects, automation developers, AI-agent builders, security contributors, and maintainers working in the US-SPURS documentation and systems ecosystem.

## Organizational Context

Before changing code, automation, architecture, or documentation, contributors should understand the current organizational model:

- Headquarters is **Division 0 / 0000**.
- US-SPURS has **13 operating divisions**.
- **Division 8 / 8000 — Science, Technology & ATLANTIS AI** is the primary technology architecture owner.
- Mission-specific systems remain accountable to the division that owns the operational requirement.
- ATLANTIS is the consolidated multi-AI system.
- SWARM is an integrated ATLANTIS module rather than a separate top-level system.

## Primary Goals

Contributors should understand:

- what US-SPURS is building
- which division owns the mission requirement
- how documentation and systems are organized
- what quality and security standards apply
- how to propose, structure, review, and publish changes
- how ATLANTIS and cross-division architecture affect implementation

## Working Principles

Contributors should build with the following assumptions:

- documentation is operational, not ornamental
- systems should be understandable by future maintainers
- technical work must map to an accountable mission owner
- security and resilience are first-class requirements
- provider-specific dependencies should remain behind clean adapters where practical
- human oversight is required for high-impact automation
- clear structure beats clever ambiguity
- experimental systems must not silently become production-critical dependencies

## Contribution Types

Contributors may work on:

- documentation expansion and correction
- system architecture definitions
- ATLANTIS modules and integration patterns
- API, event, and MCP integration guidance
- engineering standards
- deployment and recovery playbooks
- architecture decision records
- security and trust-boundary improvements
- developer tooling and repository automation

## Division Ownership

Every substantial contribution should identify its owning division or enterprise function.

Examples:

- emergency-management system → Division 1
- infrastructure platform → Division 2
- investigation or evidence system → Division 4
- healthcare-support platform → Division 5
- education platform → Division 6
- housing-support system → Division 7
- ATLANTIS, cybersecurity, AI, data, or shared technology → Division 8
- aviation, maritime, space, or mobility system → Division 9
- energy or environmental system → Division 10
- logistics, fleet, inventory, or procurement platform → Division 11
- finance, HR, payroll, or records system → Division 12
- intergovernmental or global-operations platform → Division 13

Cross-division systems should identify a lead owner and all material supporting divisions.

## Before Opening a Change

A contributor should be able to answer:

1. What problem is being solved?
2. Which division or Headquarters function owns the requirement?
3. Who will use the finished capability?
4. What systems, data, or trust boundaries are affected?
5. Does an existing ADR control this decision?
6. Does the change require security, privacy, operational, or architecture review?
7. How will the change be tested and rolled back?
8. Does this reduce user autonomy or introduce high-impact automation?

## Branch and Pull-Request Expectations

Changes should use focused branches and focused pull requests.

Pull requests should:

- describe the mission or technical problem
- identify owning divisions
- summarize implementation choices
- link relevant issues and ADRs
- disclose security and data implications
- include validation evidence
- describe rollback or reversibility

## Review Expectations

Reviews should examine:

- mission alignment
- organizational ownership
- accuracy
- security and privacy
- maintainability
- resilience
- architecture consistency
- naming consistency
- operational usefulness
- future extensibility

## Architecture Decisions

Material changes to system boundaries, identity, data ownership, provider strategy, public APIs, event contracts, deployment architecture, or ATLANTIS execution policy should use an Architecture Decision Record.

Use `docs/adr/0000-template.md` as the starting point.

## Definition of Done

A contribution is not complete merely because code or prose exists. Completion should include, as applicable:

- implementation
- automated tests
- documentation
- security review
- operational validation
- monitoring and observability
- migration or rollback plan
- updated ADRs
- ownership and support information

## Contributor Philosophy

Contributors should optimize for systems that remain useful, understandable, secure, resilient, and maintainable after the original author is no longer present.
